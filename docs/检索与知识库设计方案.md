# 劳动法 Agentic RAG —— 知识库构建与检索设计方案

> 本文档聚焦**一件事**：手上只有「中央法规」和「参考案例」两类知识，怎么把它们建成可检索的知识库，用户提问后怎么检索。
>
> 它是对《法律场景Agentic RAG设计方案.md》第 4.1 / 4.5 / 4.9 节的落地细化，与《知识库构建步骤总结.md》的流水线骨架对齐，与当前 `rag/` 代码的实际接口一致。**只做设计，不写实现代码。**

---

## 0. 一句话结论

- **建库**：把两类原始文件统一"预处理 → 抽取元数据 → 结构感知切分（父子块）→ 向量化 → 双路入库（子块向量进 Qdrant、父块全文进 MySQL）"。
- **检索**：问题理解生成检索计划 → 按意图在**两个 Qdrant 集合（法条库 / 案例库）**上做「精确匹配 + 元数据过滤 + 向量召回」多路召回 → 权威层级加权 → 合并 → rerank → 父块归组成证据包。
- 关键差异点只有一个：**不再把两类知识当一堆文本混进一个集合**，而是显式分成 `statute_db` 与 `case_db` 两个知识源，各自携带「效力层级 / 权威层级 / 效力状态」等元数据，检索时按意图路由、按权威加权。

## 1. 现状盘点

### 1.1 两类知识资产（实测）

| 类别 | 目录 | 数量 | 文件格式 | 目录层级自带的信息 |
|---|---|---|---|---|
| 中央法规 | `knowledge_data/中央法规/` | 140 txt + 3 docx | 多为 `.txt`，3 部核心法律是 `.docx` | `法律 / 行政法规 / 行政法规·规范性文件 / 司法解释 / 司法解释性质文件 / 典型案例与两高工作文件（非裁判依据）` |
| 参考案例 | `knowledge_data/劳动案例/劳动案例/` | 174 个 `.Pdf` | 全部 PDF（注意扩展名是**大写 `.Pdf`**） | `公报案例 / 指导性案例 / 典型_经典案例 / 参阅案例 / 推荐判决书_两年内` |

另有 `knowledge_data/现行有效_劳动法行政法规与司法解释清单.xlsx`，是「效力状态」的权威来源（决定某部法规是现行有效 / 已修改 / 已废止）。

**从目录结构直接能读出的、但当前代码没用的元数据**：

- 法规的 **效力层级**（法律 > 行政法规 > 司法解释 > 司法解释性质文件 > 规范性文件）——由 `中央法规/` 下的子目录名给出。
- 法规的 **版本/发布信息**——由文件名里的 `(2010修订)`、`(2018修正)`、`(FBM-CLI.2.142905)`（北大法宝 CLI 编号）、`_20071229`（日期）给出。
- 案例的 **权威层级**（指导性案例 > 公报案例 > 典型案例 > 参阅案例 > 判决书）——由 `劳动案例/劳动案例/` 下的子目录名给出。

**数据质量风险点（建库前必须处理）**：

1. 3 部核心法律（《劳动法》《劳动合同法》《劳动争议调解仲裁法》）是 `.docx`，案例全是 `.Pdf`，而现有切分脚本只 `glob("*.txt")`——不转换格式就无法处理。
2. `.Pdf` 是**大写扩展名**，且 `指导性案例/` 下有极深的数字编号嵌套目录，需要大小写不敏感、递归到任意深度的遍历。
3. `中央法规/` 里有 `典型案例与两高工作文件（非裁判依据）` 子目录——**明确标注"非裁判依据"**，不能当权威法条进 `statute_db`，需要单独打标或分流。
4. 存在 `__MACOSX/`、`.DS_Store`、`.xls` 等垃圾文件，预处理时要排除。
5. 案例 PDF 可能是**扫描件**，需要 OCR；有文本层的直接抽取即可。

### 1.2 现有代码链路（哪些可复用、哪些要动）

当前流水线（`scripts/`）与检索主链路（`rag/`）已经跑通，骨架如下：

```
原始 txt → chunk_legal_texts.py → json/（父子块）
         → embed_json_children_ali.py → embedding_csv/（子块向量，1024 维）
         → import_parent_chunks_to_mysql.py → MySQL（父块全文）
         → upload_child_embeddings_to_qdrant.py → Qdrant（子块向量，单集合）
检索：Retriever.retrieve(plan)：embed(query) → Qdrant.search(top_k) → 父块回补 → rerank(final_k)
```

**可复用（领域无关，不动）**：`embed_json_children_ali.py`、`import_parent_chunks_to_mysql.py`、`upload_child_embeddings_to_qdrant.py`、`test_*.py`、`rag/providers.py`、`rag/evidence.py`、`rag/workflow.py` 编排、`app.py` 路由。

**要增强（CLAUDE.md 第 8 节已授权检索增强）**：

| 文件 | 现状 | 要补的 |
|---|---|---|
| `rag/retrieval.py` | 单集合、纯向量、无过滤、无精确匹配、无权威加权 | 双集合 / 精确匹配 / 元数据过滤 / 权威加权 |
| `rag/skill_router.py` | 两库固定都查、`top_k=30, final_k=5` 一刀切 | 按意图分配各源召回配额 |
| `rag/config.py` + 配置模板 | 只有 `qdrant.collection_name` 一个集合名 | 增加案例集合名（或集合映射） |
| `scripts/chunk_legal_texts.py` | 只认 `.txt`、只认 `法条/` `案例/`、不抽元数据 | 元数据抽取、目录层级打标、payload 携带元数据 |
| （新增）预处理脚本 | 无 | pdf/docx→txt、清洗、重命名、元数据抽取、排除垃圾文件 |

### 1.3 关键差距（本设计的核心增量）

一句话：**现有系统"能召回文本"，但"不知道召回的是哪类文本、效力如何、该不该信"**。法律场景里这三点直接决定答案对不对：

1. 法条和案例混在一个向量空间里，语义检索会互相干扰（问"违法解除"可能召回一堆案情而不是条文）。
2. 没有 `效力状态` / `效力层级` / `案例权威层级`，容易拿**已废止条文**或**非裁判依据**当依据。
3. 没有法条号/案号的精确匹配，用户报出"劳动合同法第46条"这种最精确的线索，反而要赌向量相似度。

## 2. 总体设计原则

1. **双知识源、双集合**：法条库 `statute_db` 与案例库 `case_db` 分开存、分开召回、合并排序。
2. **元数据一等公民**：每个 chunk 的 Qdrant payload 都带 `doc_type / authority_level / validity / source_name / title_path` 等字段，检索可过滤、可加权、可追溯。
3. **复用父子块（PDR）**：子块做向量检索（小而准），父块回补上下文（大而全），不改现有 evidence 归组逻辑。
4. **权威优先、但不迷信**：权威层级只做**软加权**（重排时的偏置项），不做硬过滤，避免把语义相关但层级低的证据全砍掉。
5. **"现行有效"默认过滤、失效条文显式标注**：默认召回现行有效；已修改/已废止条文可召回但必须带标签，供"新旧法对比"用，而非直接作为结论依据。
6. **最小改动**：所有增强落在 `retrieval.py` / `skill_router.py` / `chunk_legal_texts.py` / 配置与一个新增预处理脚本上；embedding、入库、evidence、workflow 不动。

## 3. 知识库构建设计

### 3.1 数据规范化（staging，预处理阶段做）

把两类原始数据归一到统一目录，文件名用**全局唯一数字编号**开头（编号即 `doc_id`），与现有脚本约定一致：

```
knowledge_data/
  法条/                         # 法条原文（编号 + 法规名 + 版本），全部 .txt
    001_中华人民共和国劳动法_2018修正.txt
    002_中华人民共和国劳动合同法_2012修正.txt
    ...
  案例/                         # 案例原文（编号 + 案例名/案号），全部 .txt
    501_某公司诉某员工劳动合同纠纷案.txt
    ...
  法条_metadata.json            # 法条元数据清单（doc_id → 元数据）
  案例_metadata.json            # 案例元数据清单
  json/                         # 切分结果（父子块，含元数据）
  embedding_csv/                # 子块向量
```

**编号段规划**（避免两类编号撞车，也方便肉眼区分）：

- 法条：`001–499`
- 案例：`501–999`

> 现有 `中央法规/`、`劳动案例/` 是原始来源目录，**保留不动**；预处理脚本把它们"转换 + 清洗 + 重命名 + 抽元数据"后输出到 `法条/`、`案例/`。切分脚本继续只认 `法条/`、`案例/` 下的 `.txt`，逻辑不变。

### 3.2 预处理步骤（新增脚本 `scripts/preprocess_legal_raw.py`）

按序执行：

1. **格式转换**：
   - `.docx`（3 部法律）→ 文本（`python-docx` 抽正文段落）。
   - `.Pdf`（案例）→ 文本：先用 `pdfplumber`/`PyMuPDF` 抽文本层；抽不到（扫描件）走 OCR（如 `paddleocr`/`tesseract`）。大小写不敏感、递归到任意深度遍历。
2. **清洗**：去页眉页脚、水印、网站导航、`__MACOSX`/`.DS_Store`/`.xls` 等垃圾；统一全角/半角；规范化"第X条 / 第X款 / 第X项"编号写法。
3. **抽取元数据**（见 3.3），写入 `法条_metadata.json` / `案例_metadata.json`。
4. **重命名**：按编号段规则生成 `编号_名称.txt`，全局唯一、三位补零。

### 3.3 元数据模型（本设计的核心增量）

**法条元数据（`法条_metadata.json`，每条对应一个 doc_id）**：

```json
{
  "doc_id": "002",
  "doc_type": "statute",
  "title": "中华人民共和国劳动合同法",
  "source_name": "劳动合同法",
  "authority_level": "法律",              // 法律/行政法规/司法解释/司法解释性质文件/规范性文件
  "issuing_authority": "全国人大常委会",
  "document_number": "主席令第65号",
  "publish_date": "2007-06-29",
  "effective_date": "2008-01-01",
  "revision": "2012修正",
  "validity": "现行有效",                // 现行有效/已修改/已废止/未生效
  "binding": true,                        // false = 非裁判依据（如两高工作文件）
  "fbm_cli_code": "FBM-CLI.2.108577"
}
```

- `authority_level` 来自 `中央法规/` 子目录名。
- `revision` / `publish_date` / `fbm_cli_code` 从文件名解析（正则）。
- `validity` **以 `现行有效_劳动法行政法规与司法解释清单.xlsx` 为准**交叉核对；清单外的默认"需人工确认"，不要默认"现行有效"。
- `binding=false`：`典型案例与两高工作文件（非裁判依据）` 目录下的材料——默认**不进 `statute_db`**（或进但 `binding=false` 且回答时不得作为裁判依据引用）。本文推荐：该目录里的**典型案例**归入 `case_db` 并标 `authority_level=工作文件发布案例`、`binding=false`；**工作文件**单独归档，不进两库。

**案例元数据（`案例_metadata.json`）**：

```json
{
  "doc_id": "601",
  "doc_type": "case",
  "title": "彭宇翔诉南京市城市建设开发（集团）有限责任公司追索劳动报酬纠纷案",
  "source_name": "彭宇翔诉南京城建公司追索劳动报酬纠纷案",
  "authority_level": "指导性案例",       // 指导性案例/公报案例/典型案例/参阅案例/推荐判决书
  "guidance_number": "指导案例182号",     // 仅指导性案例有
  "case_number": "（2021）苏01民终XXXX号",
  "court": "南京市中级人民法院",
  "instance": "二审",                    // 一审/二审/再审
  "judge_date": "2021-XX-XX",
  "cause": "追索劳动报酬纠纷",
  "crime": null,
  "binding": true                         // 指导/公报/典型/参阅为 true；推荐判决书为 true 但 authority 最低
}
```

- `authority_level` 来自 `劳动案例/劳动案例/` 子目录名。
- `case_number` / `court` / `instance` / `judge_date` / `cause` 从案例正文用正则抽（案号模式 `（\d{4}）…民…第…号`、`指导案例N号`）；抽不到的留空，交给后续人工补全。
- `guidance_number`：指导性案例从文件名/正文抽取"指导案例N号"，这是**类案检索里最强的匹配键**。

### 3.4 切分策略（在 `chunk_legal_texts.py` 基础上细化）

保持现有父子块长度约定：**子块 150–500 字、父块 1000–3000 字**，`parent_id = {doc_id}_p###`，`chunk_id = {doc_id}_c###`。

**法条（`statute`）**：

- 结构树：`编 → 章 → 节 → 条 → 款 → 项 → 目`。
- **子块 = 一条**（超长按句边界硬切、过短相邻合并），`title_path` 形如 `劳动合同法 > 第三章 > 第四十六条`。
- **父块 = 章/节**（一个父块含若干相邻条文，为"条"提供上下文）。款/项不单独切开。

**案例（`case`）**：

- 按要素切段：`当事人 / 基本案情（案件事实）/ 争议焦点 / 裁判理由（本院认为）/ 裁判结果 / 裁判依据 / 裁判要旨`。
- 子块 = 一个要素段落内按句边界切出的 150–500 字片段；`title_path` 形如 `彭宇翔诉…案 > 裁判理由`。
- 父块 = 整篇案例（或"争议焦点 + 裁判理由 + 裁判结果"这组说理段）。
- **检索侧重点**：类案检索真正要匹配的是**争议焦点 + 裁判理由/裁判要旨**。因此给"裁判要旨 / 争议焦点 / 裁判理由"段打 `is_holding=true` 标记，检索时作为高相关信号（见 4.2）。

### 3.5 JSON 结构与 Qdrant payload 设计

切分输出的 JSON 在现有结构上**只加一个顶层 `metadata` 字段**（向后兼容，现有 embedding/入库脚本只读 `parents`/`children`，不受影响）：

```json
{
  "doc_id": "002",
  "source_path": "knowledge_data/法条/002_中华人民共和国劳动合同法_2012修正.txt",
  "title": "中华人民共和国劳动合同法",
  "metadata": { "doc_type": "statute", "authority_level": "法律", "validity": "现行有效", "binding": true, "source_name": "劳动合同法" },
  "parents": [ { "parent_id": "002_p001", "title_path": "…", "text": "…", "child_ids": ["002_c001"] } ],
  "children": [ { "chunk_id": "002_c001", "parent_id": "002_p001", "title_path": "…", "text": "…" } ]
}
```

**关键落地技巧**：现有 `upload_child_embeddings_to_qdrant.py` 用 `payload = dict(child)` 上传。为了让元数据进 Qdrant payload **且不改入库脚本**，在切分时把 `metadata` **扁平化合并进每个 child**：

```json
"children": [
  {
    "chunk_id": "002_c001",
    "parent_id": "002_p001",
    "title_path": "劳动合同法 > 第三章 > 第四十六条",
    "text": "……",
    "doc_type": "statute",
    "authority_level": "法律",
    "validity": "现行有效",
    "binding": true,
    "source_name": "劳动合同法",
    "is_holding": false
  }
]
```

这样 `RetrievedChunk.payload` 里天然带齐所有元数据，检索端直接读，零额外改动。

**Qdrant 集合与索引**：

| 集合 | 用途 | 向量维度 | 距离 | payload 关键字段 |
|---|---|---|---|---|
| `law_statutes` | 法条子块 | 1024 | Cosine | `doc_type, authority_level, validity, binding, source_name, title_path` |
| `law_cases` | 案例子块 | 1024 | Cosine | `doc_type, authority_level, case_number, guidance_number, cause, is_holding, title_path` |

- 对 `doc_type`、`authority_level`、`validity` 建 **payload 索引**（Qdrant 过滤用）。
- 对 `guidance_number` / `case_number` / `source_name` 建 **全文/keyword 索引**（精确匹配用），或另存一份「法规名→doc_id、条号→chunk_id、案号→chunk_id」的本地词典/倒排表。

### 3.6 入库流程（复用现有脚本）

```
① python scripts/preprocess_legal_raw.py        # pdf/docx→txt、清洗、抽元数据、重命名
② python scripts/chunk_legal_texts.py           # 法条/案例 切分，输出带元数据的 JSON 到 json/
③ python scripts/embed_json_children_ali.py     # 子块向量化 → embedding_csv/
④ python scripts/import_parent_chunks_to_mysql.py      # 父块全文 → MySQL
⑤ python scripts/upload_child_embeddings_to_qdrant.py   # 子块向量 → Qdrant
    --collection law_statutes        # 法条
    --collection law_cases           # 案例（跑两遍，分别指向法条/案例 JSON 与 CSV）
```

> 因为要分两个集合，第 ⑤ 步需要能按 doc_type 分桶上传。方案：切分脚本把法条 JSON 与案例 JSON 输出到 `json/statute/` 与 `json/case/` 两个子目录，向量化同样分目录，入库时分别指定目录 + 集合名。**脚本主体不用改，只加目录参数。**

## 4. 检索设计

### 4.1 检索主链路（复用 + 增强）

```
用户提问
  → query_understanding（意图/实体/改写 query/retrieval_targets，已存在）
  → skill_router（按意图生成 RetrievalPlan，含两库配额 + 过滤条件，增强）
  → Retriever.retrieve(plan)（增强，见下）
        ┌─ 精确匹配层（法条号/案号/指导案例号 最高优先级）
        ├─ 向量召回层（statute_db + case_db 分别查，带元数据过滤）
        ├─ 权威层级加权
        └─ 合并 → rerank → 父块归组
  → evidence.build_evidence（父块去重聚合，已存在）
  → answer 生成 + safety 审查（已存在）
```

`Retriever.retrieve(plan)` 的增强版伪流程：

```
hits = []
for target in plan.retrieval_targets:          # ["statute_db", "case_db"]
    exact = exact_match(target, plan.query)     # 精确匹配，命中直接置顶
    filtered = qdrant.search(embed(plan.query),
                             collection=collection_of(target),
                             limit=plan.top_k_by(target),
                             filter=plan.filters.get(target))   # 元数据过滤
    hits += exact + filtered
hits = apply_authority_boost(hits)              # 软加权
ranked = rerank(plan.query, hits, plan.final_k * 4)
return top plan.final_k（含来源配额保证）
```

### 4.2 多路召回

**① 精确匹配层（最高优先级，绕过向量）**

| 匹配对象 | 触发 | 命中动作 |
|---|---|---|
| `《法规名》第X条` / `第X条` / `第X款` | 正则 + 法规名/简称词典 | 直接定位到 `title_path` 对应的 chunk，`score=1.0` 置顶 |
| 案号 `（2021）苏01民终XXXX号` | 案号正则 + 倒排表 | 定位到该案例 chunk，置顶 |
| `指导案例182号` | 正则 + 倒排表 | 定位到该指导案例，置顶 |

法规名词典需含**简称映射**：《劳动合同法》→《中华人民共和国劳动合同法》、《劳动法》→《中华人民共和国劳动法》。

**② 元数据过滤层（向量召回前/中应用）**

- 法条默认 `filter: {validity: "现行有效"}`；若用户问"新旧法对比/某年修订前"，放开过滤并给失效条文打 `已修改/已废止` 标签。
- 案例默认不过滤 `validity`（案例无所谓现行有效），按 `authority_level` 加权而非过滤。
- 问题理解抽到 `statutes`（法规名）、`jurisdiction`（地域）、时间节点时，生成对应过滤条件（如 `source_name=劳动合同法`、`judge_date>=2021`）。

**③ 向量语义召回层**

- 用 `rewritten_query`（已含法言法语）embed，两个集合分别查，各自取 `top_k_by(target)`。

**可选 ④ BM25 / 关键词层**：当前技术栈是"阿里云 embedding（稠密）+ qwen3-rerank"，Qdrant Cloud 未配置稀疏向量。第一阶段用「规则提示词 + `title_path`/`source_name` 精确匹配」充当关键词召回的低成本替代；后续需要再上 BM25（需另配 sparse vector 或自建倒排）。**本文第一阶段不引入 BM25。**

### 4.3 双知识源路由与配额（增强 `skill_router.py`）

按意图决定**查哪些库、各给多少召回名额**（`final_k=8` 为证据包上限）：

| 意图 | 检索库配额（`top_k_by`） | 说明 |
|---|---|---|
| 法条解释 | statute 30 / case 10 | 以条文为主，案例作辅助印证 |
| 案例检索 | case 30 / statute 10 | 以类案为主，法条作裁判依据 |
| 法律咨询 | statute 20 / case 20 | 需要「法条依据 + 类案支撑」两条腿 |
| 程序咨询 | statute 20 / case 10 | 时效/管辖主要靠法条，案例少 |

**来源配额保证**（防 rerank 后一边倒）：证据包最终 8 条里，当两个库都有命中时，**至少保留 1 条法条 + 1 条案例**（除非用户意图是纯法条解释，此时可全法条）。这是对现有 `evidence.build_evidence` 的一个轻量后置约束，不改变其内部逻辑。

### 4.4 权威层级加权

rerank 前先按 `authority_level` 做**软加权**（乘法系数，只微调不主导），并保留原始分用于调试：

| 法条 `authority_level` | 权重 | 案例 `authority_level` | 权重 |
|---|---|---|---|
| 法律 | 1.00 | 指导性案例 | 1.00 |
| 行政法规 | 0.95 | 公报案例 | 0.92 |
| 司法解释 | 0.92 | 典型案例/经典案例 | 0.85 |
| 司法解释性质文件 | 0.88 | 参阅案例 | 0.78 |
| 规范性文件 | 0.82 | 推荐判决书（两年内） | 0.70 |
| 非裁判依据（binding=false） | 0.50 且回答禁用 | — | — |

实现建议：`boosted_score = score * (1 + α·(weight − 1))`，取很小的 `α`（如 0.1~0.2），**把权威当作 tiebreaker 而非主排序**；最终仍以 rerank 分为主，权威权重作为「rerank 分相同时」或「乘性小偏置」参与。

### 4.5 融合与重排

- 两库命中合并，去掉重复 parent 的 chunk（精确匹配层命中直接保留）。
- 交给 `qwen3-rerank`（现有 rerank provider 已带法律 instruct）重排，`rerank_k = final_k * 4`（现有逻辑）。
- 重排后取 `final_k=8`，套 4.3 的来源配额。
- 父块归组去重交给现有 `evidence.build_evidence`（按 `parent_id` 归组、`best_score + 0.02·log1p(命中子块数)` 排序），不改。

### 4.6 证据不足与补检（复用现有设计）

`evidence` 判 `insufficient/partial` 时，由现有 workflow 的"改写查询扩大检索"逻辑补检：换关键词、放宽 `validity` 过滤、把 `top_k_by` 上调、或切到另一知识源；最多有限轮次；仍不足则明说"证据不足，建议携带材料咨询执业律师"，不编造依据。

## 6. 数据质量与治理

1. **效力状态以清单为准**：`现行有效清单.xlsx` 是 `validity` 字段的唯一权威来源，切分脚本读它做交叉核对；对不上的法规 `validity=待确认`，**不默认现行有效**。
2. **非裁判依据隔离**：`中央法规/典型案例与两高工作文件（非裁判依据）` 打 `binding=false`，回答端禁止作为裁判依据引用；典型案例分流进 `case_db` 并标低权威。
3. **新旧法版本并存**：同一法规的多个版本（如 2010/2012 修订）各自独立 doc_id 入库，靠 `revision` + `publish_date` 区分；检索默认给最新现行版本加权，但保留旧版供对比。
4. **案例权威分层，不越级援引**：普通咨询答案优先引指导性案例/公报案例；推荐判决书只作"实践倾向"参考，不作"应当参照"表述。

复用现有 `eval/eval_retrieval.py` 与 `eval/queries.jsonl`（评测口径见《检索评测方案.md》），针对本设计新增/强化四类用例：
