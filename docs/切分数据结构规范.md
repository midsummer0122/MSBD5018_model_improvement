# 法律知识库「切分后数据结构」规范

> 本文档总结自 `knowledge_data/文档切分参考/`（医学 RAG 项目的切分产物），并映射到本法律项目。
> 它规定的是**切分脚本的输出格式**——即 `embed / import / upload` 三个下游脚本消费的数据契约。只要切分结果符合本规范，下游脚本与检索链路就不需要改。
>
> 参考文件三件套（同名、不同扩展名）：
> - `.txt` —— 原始文本（切分的**输入**）
> - `.json` —— 结构化切分结果（父子块 + 元信息）
> - `.csv` —— 子块向量（切分后再向量化得到的**输出**）

---

## 0. 三件套的角色

| 文件 | 角色 | 谁产生 | 谁消费 | 说明 |
|---|---|---|---|---|
| `.txt` | 原始文本 | 人工/预处理 | 切分脚本 | 待切分的原文，字段里不含它 |
| `.json` | 切分结构 | 切分脚本 | 向量化脚本、入库脚本 | **本规范的主体**，含 doc_id / title / parents / children |
| `.csv` | 子块向量 | 向量化脚本 | Qdrant 入库脚本 | 每行一个子块的 1024 维向量 |

三者靠 `chunk_id` / `parent_id` / `doc_id` 三个 ID 关联。

---

## 1. JSON 结构（权威 schema）

顶层 5 个键（医学参考实测）：

```json
{
  "doc_id": "002",
  "source_path": "knowledge_data/上中篇/002_..._中医学的历史沿革.txt",
  "title": "上篇 > 第一章 导论 > 第一节 中医学的历史沿革",
  "parents":  [ ... ],
  "children": [ ... ]
}
```

### 1.1 顶层字段

| 字段 | 类型 | 含义 | 法律场景取值示例 |
|---|---|---|---|
| `doc_id` | str | 全局唯一文档编号（来自文件名开头的数字） | `"002"` |
| `source_path` | str | 原始 txt 相对仓库根的路径 | `"knowledge_data/法条/002_中华人民共和国劳动合同法.txt"` |
| `title` | str | 文档标题（带层级时用 ` > ` 连接） | `"中华人民共和国劳动合同法"` |
| `parents` | list | 父块数组（上下文单元） | 见 1.2 |
| `children` | list | 子块数组（检索单元） | 见 1.3 |

> 医学里某些文档类型（下篇病证）会多一个顶层 `structure_type` 字段，是**可选扩展**，不是必填。法律场景目前不需要，保持 5 键即可。

### 1.2 parent（父块）字段

```json
{
  "parent_id": "002_p001",
  "title_path": "上篇 > 第一章 导论 > 第一节 中医学的历史沿革 > 一、 中医学的起源",
  "text": "一、 中医学的起源\n……（该父块下所有子块文本用 \\n 拼接）……",
  "child_ids": ["002_c001", "002_c002", "002_c003", "002_c004", "002_c005", "002_c006", "002_c007"]
}
```

| 字段 | 类型 | 含义 |
|---|---|---|
| `parent_id` | str | 父块 ID，`{doc_id}_p001`（三位补零） |
| `title_path` | str | 该父块在标题树中的完整路径（` > ` 连接，**最深到父块边界的那级标题**） |
| `text` | str | 父块全文 = 其下所有子块文本按序拼接 |
| `child_ids` | list[str] | 归属该父块的子块 ID 列表（**有序**，与 text 拼接顺序一致） |

### 1.3 child（子块）字段

```json
{
  "chunk_id": "002_c002",
  "parent_id": "002_p001",
  "title_path": "上篇 > 第一章 导论 > 第一节 中医学的历史沿革 > 一、 中医学的起源 > （一） 卫生保健的起源",
  "text": "（一） 卫生保健的起源\n人类为了求得生存……"
}
```

| 字段 | 类型 | 含义 |
|---|---|---|
| `chunk_id` | str | 子块 ID，`{doc_id}_c001`（三位补零，**文档内全局递增**） |
| `parent_id` | str | 所属父块 ID |
| `title_path` | str | 子块在标题树中的完整路径（**最深到该子块自身这级**） |
| `text` | str | 子块正文（**含本级标题行**，即标题 + 正文） |

**注意 `text` 里带标题**：子块文本的第一行是该级标题本身（如 `（一） 卫生保健的起源`），后面是正文。这让子块即便脱离 title_path 也能自解释，也方便 embedding 时把标题语义一并编码进去。

## 2. CSV 结构

```
chunk_id,parent_id,embedding
002_c001,002_p001,"[-0.0499,-0.0140,0.0159,...1024 个浮点...]"
002_c002,002_p001,"[-0.0097,-0.0372,0.0458,...]"
```

| 列 | 含义 |
|---|---|
| `chunk_id` | 与 JSON `children[].chunk_id` 一一对应 |
| `parent_id` | 冗余存一份，便于入库脚本校验父子对应 |
| `embedding` | 该子块的向量，**JSON 数组字符串**（本项目为阿里云 text-embedding-v4，1024 维） |

规则：**一个 child 一行**；`chunk_id` 在 CSV 与 JSON 之间必须完全一一对应（不能多、不能少、不能维度错），否则 `upload_child_embeddings_to_qdrant.py` 会报错。

---

## 3. 关键切分规则（从医学参考反推）

1. **父子块长度（软约束）**：子块 150–500 字、父块 1000–3000 字。
2. **ID 三位补零**：`{doc_id}_p001` / `{doc_id}_c001`；`c` 序号在**整个文档内**连续递增（跨父块不重置）。
3. **title_path 用 ` > ` 连接**，逐级下钻，每级标题保留**完整标题文字**（如 `第一章 导论`、`一、 中医学的起源`），不是只留编号。
4. **父块边界对齐标题**：父块不是按固定字数硬切，而是把相邻子块按累计长度分组，**分组边界落在某级标题上**；父块 title_path = 这些子块共同的最深标题。
5. **长段拆多子块**：同一标题下正文超过 500 字，按句边界拆成多个子块，**多个子块共享同一个 title_path**（参考里 `（二）药物的起源` 被拆成 c003/c004，`（三）针灸…` 拆成 c005/c006/c007）。
6. **标题后的引导正文 → 标签"概览"**：当某级标题下面直接跟着一段正文（还没有下钻到下一级标题）时，这段正文自成一个子块，title_path 的叶子用 `概览` 表示（参考里 `一、 中医学的起源 > 概览`）。

## 4. 引入法律场景的映射

### 4.1 法条（条文式）映射

| 医学概念 | 法律（法条）对应 |
|---|---|
| 篇/章/节标题 | 法规的 `编/章/节`（用**完整标题**，如 `第一章 总则`） |
| `一、 二、…` / `（一）（二）…` | 条下的 `款/项`（不单独成子块，跟在上一条里，除非超长才按款/项边界拆） |
| 标题后的"概览" | 章/节前的导语（法条里罕见；多数法条没有导语，直接第一条） |
| 父块 | 章/节（含该章所有条文） |
| 子块 | 一条（`第X条`） |

法条示例：

```json
{
  "doc_id": "002",
  "source_path": "knowledge_data/法条/002_中华人民共和国劳动合同法.txt",
  "title": "中华人民共和国劳动合同法",
  "parents": [
    {
      "parent_id": "002_p001",
      "title_path": "中华人民共和国劳动合同法 > 第一章 总则",
      "text": "第一章 总则\n第一条 …\n第二条 …\n……",
      "child_ids": ["002_c001", "002_c002", "002_c003"]
    }
  ],
  "children": [
    {
      "chunk_id": "002_c001",
      "parent_id": "002_p001",
      "title_path": "中华人民共和国劳动合同法 > 第一章 总则 > 第一条",
      "text": "第一条 为了完善劳动合同制度，明确劳动合同双方当事人的权利和义务，保护劳动者的合法权益，构建和发展和谐稳定的劳动关系，制定本法。"
    },
    {
      "chunk_id": "002_c002",
      "parent_id": "002_p001",
      "title_path": "中华人民共和国劳动合同法 > 第一章 总则 > 第二条",
      "text": "第二条 中华人民共和国境内的企业、个体经济组织、民办非企业单位等组织（以下称用人单位）与劳动者建立劳动关系，订立、履行、变更、解除或者终止劳动合同，适用本法。……"
    }
  ]
}
```

- 子块 title_path 叶子用**条号**（`第一条`），因为条没有独立标题。
- 一条正文内若含多"款/项"，保持在同一子块；若一条超过 500 字，才按款/项（句边界）拆，多个子块共享同一 `> 第X条`。

### 4.2 案例（案例式）映射

| 医学概念 | 法律（案例）对应 |
|---|---|
| 篇/章/节 | 案例的**要素段落**（当事人/基本案情/争议焦点/裁判理由/裁判结果/裁判依据） |
| "概览" | 案件基本信息（当事人、案号） |
| 父块 | 整篇案例（或"争议焦点 + 裁判理由 + 裁判结果"这组说理段） |
| 子块 | 一个要素段落（按句边界 150–500 字） |

案例示例：

```json
{
  "doc_id": "601",
  "source_path": "knowledge_data/案例/601_彭宇翔诉南京市城市建设开发（集团）有限责任公司追索劳动报酬纠纷案.txt",
  "title": "彭宇翔诉南京市城市建设开发（集团）有限责任公司追索劳动报酬纠纷案",
  "parents": [
    {
      "parent_id": "601_p001",
      "title_path": "彭宇翔诉南京市城市建设开发（集团）有限责任公司追索劳动报酬纠纷案",
      "text": "当事人\n……\n基本案情\n……\n争议焦点\n……\n裁判理由\n……",
      "child_ids": ["601_c001", "601_c002", "601_c003", "601_c004"]
    }
  ],
  "children": [
    { "chunk_id": "601_c001", "parent_id": "601_p001", "title_path": "彭宇翔诉…追索劳动报酬纠纷案 > 当事人", "text": "当事人\n……" },
    { "chunk_id": "601_c002", "parent_id": "601_p001", "title_path": "彭宇翔诉…追索劳动报酬纠纷案 > 基本案情", "text": "基本案情\n……" },
    { "chunk_id": "601_c003", "parent_id": "601_p001", "title_path": "彭宇翔诉…追索劳动报酬纠纷案 > 争议焦点", "text": "争议焦点\n……" },
    { "chunk_id": "601_c004", "parent_id": "601_p001", "title_path": "彭宇翔诉…追索劳动报酬纠纷案 > 裁判理由", "text": "裁判理由\n……" }
  ]
}
```

- 案例通常 1000–3000 字 → **一篇案例一个父块**；超长案例才按"争议焦点/裁判理由"组拆多个父块。
- **类案检索重点**：`争议焦点` 与 `裁判理由/裁判要旨` 两个子块是语义匹配的主目标（见《检索与知识库设计方案.md》）。

### 4.3 意见式 / 自由文本（补充）

- **意见式**（一、二、三 / （一）（二））：与医学"一、/（一）"标题树完全同构，直接沿用 1.2/1.3 规则；一级标题做父块、二级做子块、"概览"对应每个"一、"下的引言。
- **自由文本**（批复/通知/答复）：无层级 → 不做结构化切分，按句群 150–500 字切，`title_path` 只用文档名（或按"问题/答复"两段拆），父块 = 整篇。

## 5. 法律场景的元数据扩展

医学参考只有 5 个顶层键，**不含领域元数据**。法律场景需要在顶层加一个 `metadata`（并在切分时**扁平化合并进每个 child**，让 Qdrant payload 自动携带，详见《检索与知识库设计方案.md》§3.5）：

```json
{
  "doc_id": "002",
  "source_path": "…",
  "title": "中华人民共和国劳动合同法",
  "metadata": {
    "doc_type": "statute",        // statute | case
    "authority_level": "法律",     // 法条：法律/行政法规/司法解释/…；案例：指导性案例/公报案例/典型案例/…
    "validity": "现行有效",        // 法条：现行有效/已修改/已废止；案例无此概念可省
    "binding": true,              // false = 非裁判依据
    "source_name": "劳动合同法"     // 用于答案引用显示
  },
  "parents": [ ... ],
  "children": [ ... ]
}
```

扩展原则：**`metadata` 是加法，不影响 5 键基座**——即使去掉 metadata，下游脚本照常工作；加上后，检索端才能做"权威层级加权 / 效力状态过滤"。

## 6. 与下游脚本的消费关系（契约清单）

| 脚本 | 读取 JSON 的哪些字段 | 关键约束 |
|---|---|---|
| `embed_json_children_ali.py` | `children[].chunk_id`、`children[].title_path`、`children[].text` | 用 `title_path + text` 拼 embedding 文本 |
| `import_parent_chunks_to_mysql.py` | `doc_id`、`title`、`source_path`、`parents[].parent_id/title_path/text/child_ids` | `doc_id`、`parent_id` 全局唯一，否则报 Duplicate |
| `upload_child_embeddings_to_qdrant.py` | `children[].*`（整个 child dict 作为 payload）+ CSV | JSON child 与 CSV row 的 `chunk_id`/`parent_id` 必须一一对应，维度 1024 |

**一句话契约**：切分脚本只要产出"5 键 JSON + 每 child 一行 CSV 向量"，`embed / import / upload` 三脚本原封不动就能跑。

## 附：ID 与命名速查

| 项 | 规则 |
|---|---|
| `doc_id` | 文件名开头数字，法条 `001–499`、案例 `501–999`（建议分段，见《检索与知识库设计方案.md》§3.1） |
| `parent_id` | `{doc_id}_p001`（三位补零） |
| `chunk_id` | `{doc_id}_c001`（文档内连续、三位补零） |
| title_path 连接符 | ` > `（空格 + 大于号 + 空格） |
| 子块长度 | 150–500 字（软） |
| 父块长度 | 1000–3000 字（软） |
| 向量维度 | 1024（text-embedding-v4） |
