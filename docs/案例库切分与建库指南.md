# 案例库文本切分与建库指南

> 本文档给你（负责案例库的组员）看。目标是：把 `knowledge_data/劳动案例/` 下的 PDF 案例，切成父子块 JSON，然后向量化 + 入库，和法条库一样接入检索。
>
> 案例库切分**比法条库简单**——案例没有"章/条/项"这种结构，不用做结构解析，只用**纯文本递归切分**。

---

## 0. 你的任务（一句话）

```
PDF 案例 → 抽文本+清洗(去©北大法宝) → 纯文本递归切分 → JSON → 向量化 → 入库 Qdrant + MySQL
```

---

## 1. 数据在哪、长什么样

- **位置**：`knowledge_data/劳动案例/劳动案例/`
- **5 个子目录**（代表案例权威层级，后面可作元数据用）：
  - `公报案例`、`指导性案例`、`典型_经典案例`、`参阅案例`、`推荐判决书_两年内`
- **约 174 个 PDF**，注意三个坑：
  1. 扩展名是**大写 `.Pdf`**（不是 `.pdf`），代码里匹配时要么大小写不敏感，要么写 `.Pdf`；
  2. `指导性案例/` 目录下有**很深的数字编号嵌套目录**（十几层），必须**递归遍历任意深度**；
  3. 有 `__MACOSX/`、`.DS_Store` 等垃圾文件，要排除。

---

## 2. 切分规则（纯文本递归切分，无结构）

案例**不做**"当事人/基本案情/争议焦点/裁判理由"的结构解析，整篇当普通文本切：

- **子块**：150–500 字（软约束）
- **父块**：1000–3000 字（软约束，一篇案例通常就 1 个父块）
- **递归切分优先级**：段落边界（空行 `\n\n`、换行 `\n`）→ 句边界（`。！？；`）→ 硬切
- **overlap**：递归切开后，给后一块补 30–80 字前文
- **短块合并**：<150 字的相邻短块并入前一块
- **标题**：用 PDF 文件名（去掉扩展名）当案例名，如 `上海冠龙阀门机械有限公司诉唐茂林劳动合同纠纷案`
- **doc_id**：`5` + 四位序号 → `50001`、`50002`……（全局按文件名排序连续编号；法条用了 0/1/2/3 开头，案例用 5 开头避免撞号）

## 3. 预处理：PDF → 文本 + 去 ©北大法宝

### 3.1 抽文本

用 `pdfplumber` 或 `PyMuPDF(fitz)`：

```python
# 方案一：PyMuPDF
import fitz
doc = fitz.open("xxx.Pdf")
text = "\n".join(page.get_text() for page in doc)

# 方案二：pdfplumber
import pdfplumber
with pdfplumber.open("xxx.Pdf") as pdf:
    text = "\n".join(p.extract_text() or "" for p in pdf.pages)
```

> 如果某些 PDF 是扫描件（抽出来是空的/乱码），需要 OCR（如 `paddleocr` / `tesseract`），先看有多少扫描件再决定。

### 3.2 去 ©北大法宝（必做）

每篇 PDF 末尾通常有一句版权声明，含"**北大法宝**"字样。找到它就截断：

```python
idx = text.find("北大法宝")
if idx >= 0:
    text = text[:idx].rstrip()
```

> 有的文件写"©北大法宝"、有的写"北大法宝"、有的带"www.pkulaw.com"等，统一用 `find("北大法宝")` 兜底截断即可。顺带把页眉页脚、水印也去掉。

## 4. 参考哪个脚本

**参考 `scripts/chunk_natural_paragraph_texts.py`**——这是 4 个切分脚本里最简单、最贴合"纯文本递归切分"的一个（处理批复/答复这类无结构文本）。

你要基于它改的**只有 4 处**：

| 改动点 | 原脚本 | 改成 |
|---|---|---|
| 输入 | 读 `.txt` | 先读 `.Pdf` 并抽文本（见 §3.1） |
| 清洗 | 去重 + 去"此复" | 追加"去 ©北大法宝"（见 §3.2） |
| doc_id | `CLASS_NUMBER = "1"` | `CLASS_NUMBER = "5"` |
| 目录 | `中央法规/1自然段文本类` → `json/` | `劳动案例/劳动案例/`（递归）→ `json_cases/` |

**可以直接复用的函数**（别重写，直接 import 或抄）：`norm_len`、`split_recursive`、`add_overlap`、`overlap_prefix`、`merge_short_chunks`、`title_from_filename`。

> ⚠️ 不要照抄 `chunk_chapter_texts.py`（章/节/条/项）、`chunk_article_texts.py`（第X条）、`chunk_heading_texts.py`（一、/（一））——那些是给法条的结构化切分，案例用不上。

## 5. 输出 JSON 格式（照抄规范）

输出到 `knowledge_data/json_cases/`，格式与法条库完全一致（详见仓库根目录《切分数据结构规范.md》）：

```json
{
  "doc_id": "50001",
  "source_path": "knowledge_data/劳动案例/劳动案例/公报案例/上海冠龙阀门机械有限公司诉唐茂林劳动合同纠纷案.Pdf",
  "title": "上海冠龙阀门机械有限公司诉唐茂林劳动合同纠纷案",
  "parents": [
    {
      "parent_id": "50001_p001",
      "title_path": "上海冠龙阀门机械有限公司诉唐茂林劳动合同纠纷案",
      "text": "（父块全文，即整篇案例，1000-3000字）",
      "child_ids": ["50001_c001", "50001_c002"]
    }
  ],
  "children": [
    { "chunk_id": "50001_c001", "parent_id": "50001_p001",
      "title_path": "上海冠龙阀门机械有限公司诉唐茂林劳动合同纠纷案",
      "text": "（子块，150-500字）" }
  ]
}
```

要点：
- `doc_id` / `parent_id` / `chunk_id` 命名规则同上，`parent_id = {doc_id}_p001`、`chunk_id = {doc_id}_c001`。
- 一篇案例通常 1 个父块（`title_path` = 案例名），子块是递归切出来的片段，`title_path` 也用案例名即可。

## 6. 手动建库

### 6.1 Qdrant：新建一个集合（必做）

- **集合名**：`law_cases`
- **向量维度**：`1024`
- **距离**：`Cosine`
- 建法同法条库：Qdrant Cloud 控制台点 **Create Collection** 填这三个值；或 curl：

```bash
curl -X PUT "https://8466eac6-d4cf-4974-bd9e-3815d0addcd0.ap-northeast-2-0.aws.cloud.qdrant.io/collections/law_cases" \
  -H "api-key: 你的API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"vectors":{"size":1024,"distance":"Cosine"}}'
```

> API_KEY 从 `api_key/api_config.yaml` 的 `qdrant.api_key` 里抄；URL 也从那里抄（上面这个 URL 是当前值，若配置里变了以配置为准）。

### 6.2 MySQL：不用建，复用现有库

法条库已经建好了 `law_rag` 库和 `documents`、`parent_chunks` 两张表。**案例父块直接往这两张表写**，靠 `doc_id` 前缀区分（法条 0/1/2/3 开头，案例 5 开头），不用建任何新表。

## 7. 向量化 + 入库（跑仓库里的三个脚本）

按顺序跑（都在仓库根目录）：

### ① 向量化（子块 → embedding CSV）

```bash
python scripts/embed_json_children_ali.py \
  --json-dir knowledge_data/json_cases \
  --output-dir knowledge_data/embedding_csv_cases
```

### ② 父块入库 MySQL

```bash
python scripts/import_parent_chunks_to_mysql.py \
  --json-dir knowledge_data/json_cases \
  --host localhost --port 3306 \
  --user law_user --password 你的MySQL密码 \
  --database law_rag
```

### ③ 子块向量上传 Qdrant

```bash
python scripts/upload_child_embeddings_to_qdrant.py \
  --json-dir knowledge_data/json_cases \
  --csv-dir knowledge_data/embedding_csv_cases \
  --collection law_cases
```

> ⚠️ ③ 里的 `--collection law_cases` **必须显式写**。不写的话脚本会用配置里的 `law_statutes`（法条库），把案例向量错传进法条库。

## 附：几个最容易踩的坑（务必读）

1. `.Pdf` 大写扩展名 + 深层嵌套目录 → 用 `rglob("*.Pdf")` 大小写不敏感递归，或用 `Path.rglob("*")` 过滤 `suffix.lower() == ".pdf"`。
2. **别忘了去"北大法宝"**，否则每个子块末尾都带版权水印，污染检索。
3. **doc_id 用 5 开头**，别和法条的 0/1/2/3 撞。
4. **上传必须显式 `--collection law_cases`**。
5. 切分 JSON 输出到 `json_cases/`（独立目录），别和法条的 `json/` 混在一起，否则上传时会互相污染。

## 9. 案例库建好后：检索侧怎么接入（给后续接库的人看）

案例库建好前，检索**只查法条库**（`statute_db` → `law_statutes`）。代码里已经预留了双库能力，**现在不用改**。等案例库上传成功后，按下面 3 步切到双库：

### 步骤 1：填配置

`api_key/api_config.yaml` 里把案例集合名填上（现在是空串）：

```yaml
qdrant:
  collection_name: "law_statutes"                  # 法条库（不变）
  cases_collection_name: "law_cases"   # 案例库（当前为空，建好后填这个）
```

### 步骤 2：让检索计划带上 case_db

`rag/skill_router.py` 的 `route_skills()` 里，把检索目标加上 `case_db`：

```python
retrieval_targets=["statute_db", "case_db"],   # 加回 "case_db"
```

### 步骤 3：恢复"案例检索"意图

`rag/query_understanding.py` 里加回三处（当前是删掉的状态，逆操作即可）：

1. 加回 `CASE_HINTS = ["案例", "判例", "类案", "裁判", "怎么判", "判多少", "类似案件"]`；
2. `rule_hints()` 里加回 `if any(hint in query for hint in CASE_HINTS): intents.append("案例检索")`；
3. intents 闭集里加回 `- 案例检索：希望了解类似案件的裁判情况`。

### 无需改的（已预留好）

- `rag/retrieval.py`：已支持按 `retrieval_targets` 循环查多个集合，**空集合名自动跳过**——所以步骤 1 填了集合名、步骤 2 加了 case_db 后，检索就自动查两个库。
- `rag/providers.py`：`QdrantClient.search()` 已支持 `collection=` 参数指定集合。
- MySQL：两库父块共用 `law_rag` 的 `documents` / `parent_chunks` 两张表，靠 doc_id 前缀区分（法条 0/1/2/3、案例 5），不用动。
